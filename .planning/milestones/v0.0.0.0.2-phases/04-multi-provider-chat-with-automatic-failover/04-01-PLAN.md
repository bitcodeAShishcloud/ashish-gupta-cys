<objective>
Server-side multi-provider failover for /api/chat: an ordered candidate list from the provider registry plus a per-candidate retry loop with a first-token probe, so a single provider failure no longer breaks a visitor's chat while the visitor-visible contract stays byte-identical.

Purpose: PROV-01 (config-only provider switching) and PROV-02 (exactly-one automatic retry on pre-first-token failure) — the server half of the phase goal. The admin half is 04-02.
Output: modified lib/providers.ts (orderedChatCandidates) and rewritten app/api/chat/route.ts (failover loop + probe), verified against the reachable subset of the research validation matrix.
</objective>

Await `streamProvider(candidate, upstream, { timeoutMs: <remaining> })` — call it WITHOUT the pre-validated-URL option so both SSRF gates run inside per candidate (research Section 4; T-04-02).

6. Streaming branch: when streamProvider returns ok with a stream, call the new module-local `readFirstDelta(stream)` probe (research Section 3 reference implementation): it getReader()s the stream and loops the EXACT line parsing of route L126-155 (TextDecoder with stream:true, split on newline, pop the partial tail, skip non-data lines, skip empty payloads and the [DONE] sentinel, JSON.parse in try/catch, extract choices[0].delta.content ?? choices[0].message.content). Success returns the first content piece PLUS any further pieces parsed from the SAME batch of lines (the lines array after the first piece — collect them all into a pending-deltas array so no consumed bytes are lost), the remaining partial-line tail buffer, and the held reader. EOF with zero pieces, or a read throw, is a probe failure returning an error detail (empty-response message for EOF; the thrown message otherwise) with the reader for cleanup.

7. Commit point: only when the probe succeeds, construct the SSE Response (research Section 3 — this structurally guarantees zero bytes reach the visitor before commit, R1). The ReadableStream start() first enqueues each pending delta (accumulating sentChars from their combined length), then continues the EXISTING read loop from the held reader seeded with the tail buffer — byte-identical parsing, push({delta}), mid-stream catch emitting the redacted error, and the identical finally block (sentChars===0 guard, {done:true}, controller.close(), dispose). cancel() disposes. From commit onward behavior is byte-identical to today.

8. Probe failure = pre-first-token failure for this candidate: best-effort `reader.cancel()` plus `streamed.dispose?.()` to clear the abort timer (R4 — no socket/timer leak while the next candidate runs), record the failure as lastErr (detail + status), emit ONE console.warn line in the locked format `[chat] provider "<id>" failed before first token (<short reason>); failing over` (or `; no candidates left` when this was the final candidate — provider id and short reason only, no PII, per 04-CONTEXT "Visitor experience & logging"), and CONTINUE to the next candidate. A probe failure does NOT fall back to the same candidate's buffered path (research Section 2(c) recommendation — the provider already failed pre-token; a same-provider retry doubles latency for a likely-repeat failure).

9. Non-streamable branch: when streamProvider reports the notStreamable flag, call `callProvider(candidate, upstream, { timeoutMs: <remaining> })` on the SAME candidate (capability fallback, not a failure retry — per 04-AI-SPEC "stream→buffered fallback preserved per candidate"). On success return the EXISTING buffered single-delta Response shape (route L179-192 relocated: one {delta: reply} event then {done:true}, SSE_HEADERS). On failure record lastErr and fall through to the same console.warn + continue path.

10. Any other streamProvider false result (HTTP error including upstream 429, abort/timeout, gate rejection): record lastErr from its detail/status, same warn + continue. Upstream 429 is a plain pre-token failure — no special casing (04-CONTEXT locks "429 = failure").

11. After the loop: return the EXISTING buffered error Response shape with the LAST failure — one {error: redact(lastErr.detail)} event then {done:true} (route L181-189 shape). No silent fallback, no provider names added by our code (04-CONTEXT "All-fail" decision; research R6 disposition: keep the existing detail passthrough, never add identity strings ourselves).

12. The loop is stateless per request: it never writes process.env.AI_PROVIDERS_JSON, never mutates activeId or the registry (04-CONTEXT "activeId is never modified"; T-04-04 mitigated by construction).

Implementation discipline: no new npm dependencies (04-AI-SPEC); defensive parsing everywhere (String(x ?? ""), optional-chained extraction, try/catch around JSON.parse); routes never throw — SSE failures are emitted as events.

|----------|-------------|
| visitor client → /api/chat | Untrusted message/history cross here; SSE responses (and now failover-picked error detail) flow back to the browser |
| /api/chat → N provider upstreams | Outbound fetches to env-pinned hosts; each candidate is a NEW outbound destination whose SSRF gating must run independently |
| provider upstream → visitor error path | Upstream error text (which may echo keys or brand names) is relayed to the browser through the redaction closure |
