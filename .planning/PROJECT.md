## What This Is

Personal portfolio for Ashish Gupta (B.Tech CSE Cyber Security, NIET) built as a Next.js 14 App Router app: portfolio home, markdown blog, an AI chat assistant (server-side proxy to an OpenAI-compatible provider), and a secured admin console for provider management. Visitors interact; nothing about them is stored server-side.

## Core Value

A visitor can ask the embedded assistant about Ashish's skills, projects and security topics, and the experience — including the chat itself — should feel like it was handcrafted by Ashish, not generated by a tool.

## Requirements

### Validated

Inferred from existing code (see `.planning/codebase/`):

- ✓ Portfolio home with hero, about, skills, projects, freelance, experience, certifications, blog preview, contact — existing
- ✓ Markdown blog with static per-slug rendering, search and category filters — existing
- ✓ AI chat proxy (`/api/chat`) with SSRF-hardened outbound, rate limiting, key redaction — existing
- ✓ Chat history/name/usage persisted in visitor localStorage only — existing
- ✓ Admin console: captcha-protected login, provider status, live provider test, env generator — existing
- ✓ Security headers (CSP, HSTS, frame-deny) on every route — existing

### Active — v0.0.0.0.1 (shipped 2026-11-02)

- [ ] Assistant replies stream progressively into the chat (visible token-by-token output)
- [ ] Chat UI never displays the model or provider name to visitors
- [ ] Chat and site-wide UI/copy feel handcrafted and human — no obvious AI-generated tells

### Out of Scope

- Database or server-side chat history — product decision: everything stays in the visitor's browser
- Real authentication for chat / multi-user accounts — portfolio visitor tool, not a SaaS
- Provider streaming capability discovery UI — admin console stays as-is
- CMS for blog content — content edits in `lib/content.ts` remain acceptable

## Context

- Brownfield Next.js 14.2.5 + React 18 + Tailwind/shadcn app; full map in `.planning/codebase/`
- Chat client (`components/chat-panel.tsx`) currently does a single fetch and renders the complete reply; a dots indicator shows while waiting; header shows `{model} @ {provider}` once a reply arrives
- Provider layer (`lib/providers.ts`) performs a non-streaming POST to the provider's `/chat/completions`; the provider is OpenAI-compatible so upstream SSE streaming is available
- Zero test infrastructure; verification is manual via dev server on port 3000
- The user's driving concern: the site should not read as AI-generated — copy, chat behavior and visual details must feel personal and deliberate

## Constraints

- **Tech stack**: Next.js 14 App Router, TypeScript, Tailwind + shadcn/ui — no new frameworks
- **Security**: keep SSRF gates, host whitelist, rate limits, and key redaction intact when touching the chat route; CSP `connect-src 'self'` means streaming must be same-origin SSE from `/api/chat`
- **Privacy**: no new server-side state; usage counting stays client-side
- **Compatibility**: name gate, daily limit (30), erase-data flow must keep working

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Stream via same-origin SSE proxied from the provider | CSP allows only `connect-src 'self'`; provider key must stay server-side | ✓ Shipped Phase 1 (v0.0.0.0.1) |
| Remove model/provider info from public chat UI only | Admin console still needs it for provider management | ✓ Shipped Phase 1 + re-verified Phase 4 (PRES-01 sweep) |
| Polish pass targets copy + chat visual details, not a redesign | Site already has a strong custom theme; tells are in microcopy and chat chrome | ✓ Shipped Phase 2 |
| Failover = stateless per-request retry, pre-first-token only | Serverless-unreliable in-memory state; mid-stream retry would duplicate visitor-visible text | ✓ Shipped Phase 4 (first-token commit probe; activeId never mutated) |
